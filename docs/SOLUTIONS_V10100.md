# V10.10.0 候选解决方案穷尽枚举与对比评估

> 针对"新车型(随机名称文字/图片/视频)经飞书同步组长组员数据失败",穷尽枚举 **7套独立方案 + 1套组合方案**,
> 每套均在统一基准场景下完成**真机模拟测试**(2台随机名称车型+3照片+2视频,含21MB必败视频),
> 测试代码见 `tests/test_v1010_solutions_comparison.js`(9/9断言通过),结果数据见 `tests/v1010_solutions_results.json`。

## 一、统一基准场景

| 项 | 值 |
|---|---|
| 车型 | 2台,随机名称(`⚡随机新车<x>:*测试*\|v1?`、`🚗大视频车型"引号"名`) |
| 照片 | 3张(1.5-3KB) |
| 视频 | 2个:1MB小视频 + **21MB大视频(旧版必败触发点)** |
| 判定标准 | 组长上传成功 ∧ 组员完整拉取 ∧ 字节级一致 ∧ 不触碰20MB红线 |

## 三、逐方案真机模拟测试详情

### S1 V10.5.0基线: base64内嵌JSON + upload_all整包上传 ❌

- **模拟方式**: 按旧版逻辑构造内嵌媒体base64的同步JSON,经 `httpUploadFile` 整包上传;
- **实测结果**: 同步JSON膨胀至 **29.3MB**,飞书返回 `1061043 file size beyond limit`,整包被拒;
- **结论**: 与现场故障完全一致,确认此为根因形态,必须废弃。

### S2 媒体分离 + upload_all直传 ❌

- **模拟方式**: 照片/视频分离为独立文件逐个 `upload_all` 直传(V10.6.0/V10.9.0形态);
- **实测结果**: 3照片+1小视频成功(4/5),**21MB视频被拒** `1061043`(1/5失败);
- **结论**: 媒体分离消除了JSON膨胀,但单靠分离无法覆盖现场10-50MB视频,必须叠加大文件通道。

### S3 客户端压缩至20MB内 + upload_all ⚠️

- **模拟方式**: 21MB视频按0.6压缩比转码为12.6MB后直传;
- **实测结果**: 上传成功,字节回环一致;
- **硬伤**: ①画质有损——断电操作关键帧细节可能丢失,业务不可接受;②移动端转码耗时数分钟且耗电;③>50MB素材压缩比要求苛刻;④无法保证任意素材都压得进20MB;
- **结论**: 仅适合作辅助兜底,不能作为主方案。

### S4 自建中转服务器分片聚合转发 ⚠️

- **模拟方式**: 模拟中转服务器接收4MB分片×6 → 聚合落盘,字节回环一致;
- **实测结果**: 技术上完全可行,无体积上限;
- **硬伤**: ①需自建服务器/云函数+存储(持续成本);②ICP备案/HTTPS证书;③自研鉴权与运维;④数据离开飞书合规域;
- **结论**: 对Cordova单体应用属过度设计。

### S5 飞书多维表格(Bitable)附件通道 ❌

- **模拟方式**: 按Bitable附件上传语义模拟(同源20MB限制);
- **实测结果**: 1MB小视频成功,**21MB视频被拒** `1061043`;
- **结论**: Bitable附件与云空间同源同限,且需把数据模型重构为表格记录+附件字段,迁移成本高、收益为零——此路不通。

### S6 OSS对象存储直传 + 飞书通知 ⚠️

- **模拟方式**: 模拟OSS分片上传(8MB/片×3),字节回环一致;
- **实测结果**: 技术最优(单文件5GB上限);
- **硬伤**: ①额外开通对象存储+计费;②客户端内嵌AK/SK或STS存在安全风险;③组长/组员双端改造下载通道;④数据脱离飞书管控域;
- **结论**: 运维与合规成本显著,非必要不引入第二套系统。

### S7 手动导出/导入离线兜底 ⚠️

- **模拟方式**: 组长导出离线包(29.3MB,完整携带媒体)→ 组员导入合并;
- **实测结果**: 数据完整,永远可行(功能已具备:V10.9.2导入备份);
- **硬伤**: 完全依赖人工传递(微信/U盘),无实时性,易漏传;
- **结论**: 保留为最后兜底通道,不满足"自动同步"需求。

### S2+S3 媒体分离+压缩兜底组合 ⚠️

- **模拟方式**: 先直传,失败项压缩到限内补传;
- **实测结果**: 功能闭环(直传失败→压缩补传成功);
- **结论**: 继承S3全部硬伤(有损/耗时/未必压得进),客户端逻辑复杂度陡增,对比官方分片上传性价比明显更低。

### S* 飞书官方分片上传三件套 ✅【采纳】

- **方案**: `upload_prepare`(预上传,返回upload_id/4MB定长分片) → `upload_part`×N(逐片上传+Adler-32校验和) → `upload_finish`(落盘返回file_token);
- **模拟方式**: 完整真机模拟管线——组长端 `_syncUploadPipeline()`(含21MB视频) → 组员端 `doSyncDownload()` 合并;
- **实测结果**: 一次同步成功,21MB视频走6片分片,**全程零触碰20MB红线**,组员端2台车型完整合并,字节级一致;
- **优势**: ①无损;②零额外基建(与upload_all同一权限域);③与飞书合规/管控域一致;④官方原生支持,长期可维护;
- **结论**: 综合评分第一,采纳为V10.10.0实施方案。

## 四、评分方法说明

综合评分 = 可行性(能否覆盖21MB+视频) × 数据保真(无损优先) × 基建成本(零基建优先) × 实施复杂度 × 合规性(飞书域内优先) × 用户体验(自动/实时优先)。

全部9套方案的原始测试输出与断言明细见 `tests/v1010_solutions_results.json`。
