# 资源库视频「播放源」评估方案

> 结论先行：**播放源应当与真源分离**——飞书继续当真源（编辑、替换都在飞书），
> 但**不要**让用户播放时经过飞书 API；播放走「对象存储 CDN 为主、GitHub Release 为备」。
> 依据是本机同一时段的实测：飞书 4.2 MB/s vs GitHub 0.42 MB/s（最差 94 KB/s），
> 但飞书这条路前端拿不到直链——它不是"慢不慢"的问题，是"能不能"的问题。

## 1. 要决定什么

资源库有 **66 个教学视频 / 498.1 MB**（中位 8.15 MB、最大 17.3 MB）。现在唯一的播放源是
GitHub Release 的 `media-videos` 资产（免鉴权、支持 Range，见 `js/00-bootstrap.js`
的 `MEDIA_RELEASE_BASE`）。候选源有三个：飞书云盘、GitHub Release、WorkBuddy 对象存储。

要回答的其实是两个独立问题，混在一起就会得出错的结论：

1. **谁搬得快**（传输层）——可以用同一把尺子量；
2. **谁能让前端直接播**（接入层）——这是 0/1 的判定，慢但能直连 > 快但要密钥。

## 2. 测量方法（可复现）

```bash
# 两个已接入源，每次取 4MB，各 3 次，附 2 路并发
node scripts/bench_media_sources.js --sources github,feishu --bytes 4194304 --repeat 3 --write

# 对象存储（拿到公开直链后）
WORKBUDDY_BENCH_URLS="https://cdn.example.com/a.mp4,https://cdn.example.com/b.mp4" \
  node scripts/bench_media_sources.js --sources workbuddy --write
```

脚本口径（为什么这么定）：

- **Range 请求取前 N MB**：视频播放本来就是分段取流，测全量会把"用户等首帧"这件事掩盖掉；
- **报中位 + p95 + 最差**：国内到 GitHub 的抖动本身就是结论，只报中位会把 21 秒那次当噪声；
- **并发 2 路**：CDN 与源站的差别在这里最明显（共享带宽 vs 独占连接）；
- **失败单独统计**：超时不算 0 KB/s 混进均值，会美化结果。

判定一个源"能用"的三个硬条件：**免鉴权公开直链、支持 Range(206)、有 CDN 缓存**。
缺任一条，后面的速度分数就没有意义。

## 3. 实测结果（2026-11-24 15:31，同一网络、同一时段）

共跑两轮（每次 4MB × 3 次、2 路并发），两轮结论一致，抖动反而更清楚：

**第一轮**

| 源 | HTTP | TTFB 中位 | TTFB p95 | 吞吐中位 | 吞吐最差 | 2 路并发合计 | Range |
|---|---|---|---|---|---|---|---|
| GitHub Release | 206 | 0.65s | 0.78s | 418 KB/s | 94 KB/s | 1294 KB/s | ✅ |
| 飞书 drive 下载（带 token） | 206 | 0.61s | 0.79s | **4205 KB/s** | 3151 KB/s | 6976 KB/s | ✅ |

**第二轮**（`docs/media_source_bench.json` 里留痕的就是这轮）

| 源 | HTTP | TTFB 中位 | TTFB p95 | 吞吐中位 | 吞吐最差 | 2 路并发合计 | Range |
|---|---|---|---|---|---|---|---|
| GitHub Release | 206 | 0.61s | 1.19s | **138 KB/s** | 38 KB/s | 1677 KB/s | ✅ |
| 飞书 drive 下载（带 token） | 206 | 0.63s | 0.63s | **4037 KB/s** | 4015 KB/s | 7729 KB/s | ✅ |
| WorkBuddy 对象存储 | — | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |

最关键的证据在逐次明细里：GitHub 同一个 4MB 片段，三次分别是 **1.94s / 29.58s / 107.96s**
（2113 → 138 → 38 KB/s），第一轮还有一次 **45 秒超时零字节**。飞书六次全部落在
3.1–4.8 MB/s，几乎不抖。也就是说 GitHub 的问题不是"慢一点"，而是**尾部不可预测**——
一个 8MB 视频可能是 6 秒，也可能是 3 分半，或者干脆放不出来。对"点开就要看"的教学视频，
这个尾部比平均值重要。

> 注意：飞书这一行是用 APK 样本测的传输层（视频的 file_token 需要现场翻目录才知道，
> 脚本支持 `FEISHU_BENCH_FILE_TOKEN` 指定）。同一 CDN 边缘节点，口径一致。

## 4. 打分矩阵（权重 × 1–5 分）

| 维度 | 权重 | 为什么给这个权重 |
|---|---|---|
| 播放体验（TTFB/吞吐/抖动） | 30 | 用户直接感知，且不可用缓存掩盖 |
| 前端可直连（免鉴权） | 20 | 0/1 判定：要密钥就等于必须多养一个服务 |
| 成本 | 15 | 498MB 量级下费用不高，但流量会随用户数线性增长 |
| 运维复杂度 | 20 | token 刷新、限流、缓存失效都在这里 |
| 可持续性/锁定 | 15 | 迁移一次的成本远大于每月省下的钱 |

| 源 | 体验 | 直连 | 成本 | 运维 | 可持续 | 加权总分 |
|---|---|---|---|---|---|---|
| GitHub Release | 1 | **5** | **5** | 3 | 2 | **2.95** |
| 飞书云盘 | **5** | **1** | 4 | 2 | 3 | **3.15** |
| WorkBuddy 对象存储 | 待测(预期 4–5) | **5** | 待测(预期 4) | 待测(预期 4) | 待测(预期 4) | **预期 ≈4.2** |

**一票否决项**（任一命中即出局，不参与加权）：前端需持密钥；不支持 Range；
无公开读；单文件上限 < 20MB；无法设置缓存头。

按此规则：飞书在"前端可直连"上被否决——它只能当**真源**或**经代理后的后端源**。

## 5. 向 WorkBuddy 需要确认的 12 个问题

在拿到对象存储账号后，先把这张表填满，再跑基准脚本：

1. 是否 S3 兼容（可否用 `aws s3 cp` / `rclone` 直传）？
2. 桶能否设为**公开读**，给出稳定的匿名 HTTPS 直链？
3. 是否前置 CDN？`Cache-Control` 可自定义吗？默认 TTL 多少？
4. 是否支持 **Range**（视频拖动必备）与断点续传？
5. 单文件上限多大？（我们的最大视频 17.3MB，但要留余量）
6. 免费额度：存储 GB、月流量 GB、请求数？超出后单价？
7. 是否有并发/带宽限速？
8. 支持自定义域名 + 免费 HTTPS 证书吗？
9. 有访问日志与缓存命中率可看吗（排障需要）？
10. 覆盖写/删除的一致性如何（视频替换后用户会不会拿到旧缓存）？
11. 数据存放地区（境内/境外）？境内直连速度如何？
12. 有无 SLA？故障时的降级建议？

## 6. 推荐架构：多源回退链

```
飞书云盘（真源，只给同步任务用）
   └─▶ 同步任务（已有 15 分钟流水线 + secrets）
         ├─▶ 对象存储 CDN  ← 播放主源（命中率最高，免鉴权，支持 Range）
         └─▶ GitHub Release ← 播放备源（同资产，CDN 不可用时回退）
```

播放侧按 `CDN → GitHub → 已下载缓存` 三级回退；三级都失败才提示「稍后再试」，
并把失败上报到已有的 `js/17-error-report.js` 通道（这样"哪个源在挂"是可观测的）。

**为什么不让飞书直接当播放源**：前端要么持 `tenant_access_token`（等于泄露 app secret），
要么多养一个代理服务；而且飞书普通云盘文件**没有**匿名临时链接——实测
`batch_get_tmp_download_url` 对普通文件返回空数组（该接口只对 media 类型有效）。
换句话说，飞书那条 4.2 MB/s 的路径，只有"我们自己的服务"能用，用户用不上。

## 8. 验收标准（可量化，写进 CI）

- 主源 TTFB p95 ≤ **1.5s**；吞吐中位 ≥ **1.5 MB/s**；最差 ≥ **0.8 MB/s**；
- 全部视频 **206 + Content-Range** 校验通过；
- 2 路并发合计 ≥ **2.5 MB/s**；
- 4G 模拟（200KB/s、150ms RTT）下 8MB 视频首帧 ≤ **3s**（无头 Chrome 430×932 实测）；
- 主源不可达时，回退到备源的耗时 ≤ **2s**（不能先等 45 秒超时）。

## 9. 复现与留痕

- 测量脚本：`scripts/bench_media_sources.js`（无第三方依赖，CI 可跑）
- 结果留痕：`node scripts/bench_media_sources.js --write` → `docs/media_source_bench.json`
- 每次改动播放源或 CDN 配置后重跑一次，把 JSON 一起提交——结论要能被复核。
