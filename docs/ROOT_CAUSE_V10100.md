# V10.10.0 飞书同步失败根因分析报告

| 项目 | 内容 |
|---|---|
| 故障现象 | 上传的新车型数据(含随机名称文字、图片、视频)通过飞书同步组长→组员数据失败 |
| 影响范围 | 全部携带>20MB视频的新车型同步;组员端永远拉不到新数据 |
| 定位版本 | V10.9.2(故障)→ V10.10.0(修复) |
| 报告日期 | 2026-08-31 |
| 定位方法 | 代码链路静态分析 + 飞书官方文档比对 + 高保真Mock服务器故障复现 |

---

## 一、故障现象

现场操作流程:

1. 组长在数据同步页新增车型,填写**随机名称**(含空格、特殊符号、中文、emoji等),拍摄/选择**照片**与**视频**(现场拍摄视频普遍10-50MB);
2. 点击"上传同步"后,组长端表面无明确报错或仅提示部分失败;
3. 组员端点击"同步下载",**永远拉不到新车型数据**——同步失败。

关键特征:

- 只要新车型携带**单个>20MB的视频**,同步必败;
- 纯文字/小图片车型偶发成功,故障与媒体体积强相关;
- 随机名称(特殊字符/超长名)进一步加剧失败概率。

## 二、根因链路(逐层剖析)

### 根因①(主因): 飞书 upload_all 单文件20MB硬上限 + 大视频直传必败

飞书开放平台云空间 `POST /drive/v1/files/upload_all`(全量上传)接口官方明确限制**单文件≤20MB**,超限返回错误码 `1061043 file size beyond limit`。

旧版上传管线中,视频经 `syncUploadVehicleVideos()` 分离为独立文件后,仍统一走 `httpUploadFile()`(即 upload_all 单发直传)。**任何>20MB的视频上传必然失败**——这是第一张倒下的多米诺骨牌。

### 根因②(放大链): 失败视频 base64 滞留 → 同步JSON膨胀 → 整条管线中断

视频上传失败后,其 `data:video/mp4;base64,...` 原始数据**滞留在 `videoPaths` 中未被替换为云端路径**。随后构造的 `vehicle_sync_data.json` 把这些巨型 base64 原样内嵌:

```
21MB视频 → base64编码 ≈ 28MB → 同步JSON ≥ 29.3MB(实测)
```

29.3MB 的 JSON 本身又超过 upload_all 的 20MB 上限 → **同步数据主文件上传也失败** → 组员端 `doSyncDownload()` 拉到的仍是旧数据或空数据。单个大视频的失败被放大为**整条同步管线中断**——这正是"组员永远拉不到新车型"的直接机制。

旧版对此**无任何体积预检与诊断**,巨大 JSON 被静默推上(或推不上)云端,故障完全隐形。

### 根因③(配置缺陷): cfg 漏配 syncSub → 同步数据落错目录被清理

`_syncUploadPipeline()`、`doSyncDownload()`、`checkCloudDataUpdate()` 三处 cfg 字面量**遗漏 `syncSub` 字段**,导致同步 JSON 被上传到"APP数据备份"根目录而非约定的"同步数据"子目录;随后数据分仓迁移清理逻辑把根目录文件当旧档删除——即使上传侥幸成功,组员端也找不到数据文件。

### 根因④(诱因): 随机名称未清洗 → 合规拒绝

现场新增车型名称完全随机,常含 `\/:*?"<>|`、控制字符、emoji、超长串。飞书云空间对文件名有合规校验,非法名称返回 `1061109` 拒绝。旧版未做文件名清洗,随机名称直接触发上传拒绝。

### 根因⑤(可靠性缺口): 无频控/无重试/无校验

- 飞书上传类接口限制 **5 QPS**,旧版并发连发易触发 `1061045` 频控;
- 分片事务 24 小时过期(`1061021`)、弱网抖动均无重试兜底;
- 无校验和,弱网位翻转无法被发现。

### 故障链全景图

```
现场拍摄21MB视频
   │
   ▼
①upload_all直传 ──20MB硬上限──▶ 1061043必败
   │
   ▼
②base64滞留videoPaths(无诊断)
   │
   ▼
同步JSON膨胀至29.3MB ──超20MB──▶ 主数据文件上传也失败
   │                                    │
   ▼                                    ▼
③cfg漏syncSub→落错目录被清理    ④随机名称→1061109合规拒绝
   │
   ▼
组员端doSyncDownload拉不到新数据 ──▶ 【故障现象: 同步失败】
```

## 三、证据清单

| 证据 | 来源 | 结论 |
|---|---|---|
| upload_all 单文件≤20MB | 飞书开放平台官方文档 `上传文件(upload_all)` | 根因①成立 |
| 分片上传三件套(upload_prepare/upload_part/upload_finish)支持大文件,4MB定长分片 | 飞书官方文档 `分片上传` | 修复路径可行 |
| `1061043 file size beyond limit` | 飞书官方错误码表 | 与现场失败码一致 |
| B4 回归对照测试: 21MB直传必被拒 | `tests/test_v1010_sync_e2e.js` B4 | 根因在受控环境100%复现 |
| S1 基线模拟: JSON膨胀29.3MB被拒 | `tests/test_v1010_solutions_comparison.js` S1 | 根因②量化证实 |
| 上传类接口5QPS限制 | 飞书官方频控说明 | 根因⑤成立 |

## 四、修复结论

主修复: **接入飞书官方分片上传三件套**(同权限域、零额外基建),配合媒体分离、文件名清洗、QPS门控、重试退避、JSON体积守卫,构成完整修复(详见 `docs/SOLUTIONS_V10100.md` 与 `docs/RELEASE_V10100.md`)。

验证: 18项真机模拟E2E测试全部通过,含21MB大视频组长→组员完整闭环(详见 `docs/TEST_REPORT_V10100.md`)。
