# V10.26.3 发布说明（照片引用修复版）

- **发布日期**：2026-11-23
- **版本号**：10.26.3（versionCode 102603）
- **一句话总结**：31 条「照片声明在车型目录、文件却在 `_共享/`」的 404 引用，已在同步管线里自动回写，并在流水线与 CI 各加一道校验。

## 问题

`migrate_media_to_folders.js` 曾把「被 ≥2 个车型引用」的照片统一挪进 `vehicle_images/_共享/`，**但没有回写引用**。数据里仍然写着：

```
vehicle_images/比亚迪海豚EV/image1.jpeg     ← 引用
vehicle_images/_共享/image1.jpeg            ← 实际文件
```

后果：**组长在飞书云盘/仓库里看得到图，App 里却 404**。审计把这类问题单列成「引用失配（可自动修）」，当前有 **31 条**。

更麻烦的是：每次云端同步都会把「车型目录路径」重新写回产物，所以**手工修一次也白搭** —— 下一轮同步又回来了。

## 修复

| 项 | 内容 |
|---|---|
| 管线 | `sync-web-data.yml` 在 `gen_vehicles_data` 之后自动执行 `fix_shared_refs.js`（幂等），把失配引用改写到 `_共享/` |
| 卡口①（流水线） | 生成映射/索引前 + **提交前**各跑一次 `fix_shared_refs.js --verify` |
| 卡口②（CI） | `ci.yml` 新增独立 step「照片引用完整性」，退出码直接传播（**不加 `|| true`**） |
| 数据 | 本次已回写：`vehicles_data.js` 31/31、`web-data` 镜像 31 处 |

## 效果（`npm run audit:media`）

## 为什么不会再退化

1. 每次同步都会先修复再生成映射/索引，产物里不再出现"文件在 `_共享/` 却指向车型目录"的引用；
2. 提交前的 `--verify` 与 CI 的「照片引用完整性」step 会在任何一次回归时直接红；
3. 新测试 `tests/test_v10263_shared_refs.js`（16 断言）用**与 App 完全相同**的路径解析规则（`js/00-media-paths.js#resolveLocalFile`）复核 0 失配，并校验管线顺序、CI 接线与幂等性。

> 注意：`--verify` 只拦「文件在别处却没回写」；「全树都没有这个文件」属于真缺失，仍以 WARN 报告（需要业务补拍），不会误拦发版。
