# V10.20.1 诚实空态 + 同步防倒退版 — 发布说明

> 版本号：10.20.1 ｜ versionCode：102001 ｜ 发布时间：2026-10-06

## 一句话

照片丢了就**明说丢了**：删掉会伪装的灰图占位，详情格与列表缩略图直接写明「照片缺失 · 云端与本地均无此文件」；同时修掉一个会让网页端车型数量**倒退回 82 车**的同名副本隐患，并把本轮同步批次新增的 5 处乱码补齐到校正表。

## 背景：为什么必须改照片空态

22 个车型 / 65 张照片在飞书账号重置期间丢失。已做的查证（不是猜测）：

- 用线上凭据遍历云盘 `APP数据备份/vehicle_images`，并额外搜索 6 个候选目录（含 `05_待清理重复媒体`）及其全部子目录 —— **65 张全部 0 命中**
- 命名形态学：全云盘不存在任何新命名（`<车型名>_p<N>_<hash>`）文件，指向"数据在账号重置时就没了"，而非 token / 路径问题
- 唯一可能的恢复源是已重置的旧飞书租户。经确认，用户选择**放弃恢复，改做诚实空态**

在此之前，加载失败的处理是：

```js
// 旧行为
img.src = _imgPlaceholder();   // 一张写着"照片暂缺"的灰图
```

灰图带来的问题是**它太像"还没加载完"** —— 格子照样可点击、右下角照样挂着「前脸照片」标签、鼠标照样是手型。现场用户无法判断"文件真没了"还是"再等等就有"，只能反复刷新。这是骗用户的空态。

## 本次内容

### 1. 诚实空态（js/06-media.js）

| 位置 | 旧行为 | 新行为 |
|---|---|---|
| 详情页照片格 | 换成灰图 `img.src` | `showPhotoMissing()`：整格替换为虚线框 + 「照片缺失 / 云端与本地均无此文件」，移除 `onclick` 与部位标签，`cursor: default` |
| 列表卡片缩略图 | 换成灰图 | `showThumbMissing()`：64×48 内最小化呈现「缺失」+ 划掉的相框图标 |
| 查看器大图 | 画一张"带车名的照片相框"装饰图 | `_photoViewerMissingSvg()` 按原因区分两种缺失（见下） |

**两种缺失必须区分文案**，因为处置方式完全不同：

- `missing` —— 登记了文件名但云端本地都取不到 → 「**照片文件缺失** / 云端与本地均无此文件，请联系组长补传」
- `never` —— 该车型压根没登记这一张 → 「**该车型暂未上传照片**」（处置是重新拍摄上传，不是补传）

同时删除了 `_imgPlaceholder()`，并在原位置留下删除理由注释，防止后人误加回。

附带修掉一个真实 bug：`_photoViewerMissingSvg()` 里车名先 `_xmlEsc` 一次、再拼进副标题后又 `_xmlEsc` 一次，属于**双重转义** —— 车名里的 `&` 会被渲染成字面量 `&amp;amp;`，`<` `>` 同理。

### 2. web-data 同步防倒退（scripts/sync_web_data.js）

**问题**：飞书「同步数据」目录下现存两份**同名** `vehicle_sync_data.json`：

| 副本 | 体积 | 车辆数 | 修改时间 |
|---|---|---|---|
| copy1 | 98,347 B | 100 | 2026-10-03 |
| copy2 | 77,765 B | 82 | 2026-09-06 |

旧 `feishuFindFile()` 命中第一个就 `break`，**取到哪一份完全取决于 API 返回顺序** —— 这就是此前"网页端一度回到 82 车且不可复现"的根因。

**修复**：

- 新增 `pickNewestByName(candidates)`：按 `modified_time` 取最新；无时间戳者排最后；null 安全；不改动入参
- `feishuFindFile()` 改为收集全部同名候选后交给它选择

**纵深防御（写入前熔断）**：新镜像车辆数少于已有产物且两者均 > 0 时，拒绝写入、保留原产物、提示"疑似取到同名陈旧副本"；组长确实下架车型时加 `--force` 放行。与既有的 0 车熔断构成上下界双闸。

> 云端那份 82 车的陈旧副本**未删除**（按用户决定，本次只改代码不动云端文件）。代码侧已能稳定选中最新副本。

### 4. 自动派生校正层（结束手工 treadmill）

上一节末尾提过"这已是第 5 次追加同类条目"。写完发布说明后，cron 又推了一批新的 —— 而且**形态迁移**了：

| 轮次 | id=80 的损坏形态 | 已收录条目 |
|---|---|---|
| 第 1 批 | `取出车???匙` | 匹配 |
| 第 2 批 | `取出??钥匙` | **不匹配**（同一句，坏的位置变了） |

这说明**手工校正表在结构上是错的工具**：它在追一个每次同步都会重新随机的目标，永远差一轮。

**做法**：把损坏串的 U+FFFD 连续段当通配符，在**本仓干净语料**里求解。

| 约束 | 说明 |
|---|---|
| 段长用 `1..n+1` 而非等长 | 双重编码下 FFFD 个数 ≠ 原字符数；等长通配实测 **0/3** 命中，宽松通配 **3/3** 命中 |
| 必须**唯一命中** | 0 命中 / 多解一律不动，宁可不改不可改错 |
| 字面上下文 ≥ 4 字 | 模式过宽就拒绝猜测 |
| 每条都打印 `from → to` | CI 日志可审计 |
| 未解决的照旧 `[WARN]` | 交人工收录，不静默放行 |

**证据**：

- 本轮 3 处损坏：**3/3 唯一命中，0 歧义**
- 回放历史 30 条人工条目：自动派生**复现 29 条，0 条纠错**（剩下 1 条确属真歧义，自动派生同样拒绝 —— 行为正确）
- **变异自证**：把"字面上下文 ≥ 4"改成恒不成立后，`test:vehicle-integrity` 的 I3a 立刻转红（产物残留 7 个替换符），证明"绿"确实来自自动派生，而不是手工表碰巧兜住

手工表 `KNOWN_CORRUPTIONS` 保留并**优先执行**（作为 override），两者互补。
