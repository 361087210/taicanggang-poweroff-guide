逐项方案详情

现状均基于 V5.3.1 代码库实测核对，非泛化描述
1

离线模式

高 · P1
现状UI 层已零 CDN 本地化（Tailwind/SheetJS/jsPDF 均入 vendor/），断网可浏览 73 车型本地数据；但用户数据（审批状态/备份/账号）每次都实时拉飞书，断网即不可用，视频云端回退链同样依赖网络。
方案① 云数据快照：飞书拉取成功后写入 localStorage 快照（账号表/审批结果/待审列表），启动时先渲染快照再后台刷新（stale-while-revalidate），网络异常时顶部展示"离线数据 · 更新于 HH:mm"横幅；② 视频按需缓存：播放成功的云端视频用 cordova-plugin-file 落盘本地，二次播放零流量；③ 快照版本号与数据分仓目录对齐，避免新旧格式冲突。
涉及: demo.html 数据层风险: 快照体积(账号表&约50KB)验收: 飞行模式下审批状态/视频可查看
2

断点续传

中 · P2
现状组长上传教学视频（≤20MB）与照片为整包一次性传输，弱网中断即全部重来；20MB 已逼近飞书单文件上限，成功率受网络制约。
方案① 接入飞书云文档分片上传（upload_all → upload_prepare/upload_part/upload_finish 序列）；② 本地维护断点记录表（文件指纹 + 已传分片偏移），中断后重进自动从断点继续；③ advanced-http 原生通道透传分片，复用现有 CORS 修复成果；④ 上传进度条细化到分片粒度。
涉及: 上传模块依赖: 飞书分片API配额验收: 弱网中断3次仍能续传成功
3

服务端生成缩略图

中低 · P3
现状照片压缩在客户端完成（最长边 800px / 质量 70%），列表缩略图与详情图同源加载；无任何服务端，链接原文方案在本架构下需变形。
方案替代路径（AI 时代无后端解法）：在 CI 流水线构建期用 sharp 对 vehicle_images/ 批量生成 240px 列表缩略图目录（thumbs/），随 APK 内置双份图——列表加载缩略图、详情按需加载原图；APK 增量约 2MB，换列表滚动内存占用降 60%。云上传照片仍走客户端压缩，保持上传链路不变。
涉及: android-release.yml + demo.html收益: 列表流畅度验收: 低内存机型滚动不掉帧
4

消息中心

高 · P1
现状组员申请通知靠 60 秒轮询 + Toast，提示即逝、错过无痕；审批结果、同步失败、版本更新各自为政，无统一入口。
方案① 统一消息表：类型枚举（注册申请/审批结果/同步失败/版本更新/视频上传完成），结构 {type, title, body, bizId, read, createdAt}；② localStorage 持久化 + 飞书「APP数据备份/messages.json」增量合并，跨设备已读同步；③ 底部 Tab 增消息入口 + 未读红点徽标；④ 轮询命中新事件改写为消息落库而非 Toast，Toast 仅作即时补充。
涉及: 轮询器 + 新消息页依赖: 离线模式快照验收: 错过轮询窗口仍可回看全部消息
5

数据看板

中 · P2
现状无任何统计视图；车型数/匹配率数据实际已在映射表（73 车型 / 64 视频引用 / 0 照片缺失）中就绪，缺的只是展示层。
方案① 组长可见看板页：车型总数、品牌分布、视频匹配完成率（读 vehicle_media_mapping.json，映射表已是 CI 自动生成的可信数据源）；② 行为计数：视频播放次数/分享次数/导出次数本地累计（localStorage 计数器），隐私敏感不上云；③ ECharts 本地化进 vendor/，延续零 CDN 原则；④ 看板作为组长端首页可选模块。
涉及: 新看板页 + vendor数据源: 映射表(问题4产物)验收: 匹配率与映射表数字一致
6

操作日志

中 · P2
现状数据增删改无审计痕迹，出问题无法回溯"谁在何时改了什么"；审批动作虽上云但无完整操作链路记录。
方案① 结构化事件 {who, role, action, target, before, after, device, ts}，统一由操作总线发射（所有写操作过同一入口）；② 本地环形缓冲（最近 500 条）+ 每日增量上传飞书「APP数据备份/audit_logs/」；③ 组长端日志查询页（按人/按时间/按动作筛选）；④ 日志写入失败不阻塞业务主流程。
涉及: 操作总线 + 查询页依赖: 消息中心同期建设验收: 删除车辆后日志可查前后值
7

权限分级

低 · P3
现状已有组长/组员两级（approved_users.json + 角色字段），功能边界基本清晰；链接原文设想的"管理员"层级当前场景暂无真实需求方。
方案① 按需新增管理员角色：可管理组长账号、全局参数（轮询频率/备份目录）、查看全量操作日志；② 权限矩阵表驱动（功能 × 角色布尔矩阵），替代散落各处的 if(role) 判断；③ 路由守卫统一收口，未授权跳转登录而非白屏。仅当出现"多班组隔离"需求时升级，避免过度设计。
涉及: 账号体系 + 路由原则: 不过度设计验收: 越权访问被守卫拦截
8

数据加密

高 · P1
现状账号密码明文存于飞书云端 approved_users.json（V5.4 已排期 SHA-256 + 盐）；localStorage 中 Secret、离线快照均为明文；传输侧已是 HTTPS + 飞书 tenant_token。
方案① 密码：SHA-256 + 每用户随机盐（V5.4 承接，存量明文首登强制迁移）；② 本地敏感字段：WebCrypto AES-GCM 加密 localStorage（密钥由设备指纹派生），覆盖 Secret/账号快照/消息表；③ 传输：保持 HTTPS，禁用任何明文回退；④ 加密层做成统一 crypto util，供离线模式与消息中心复用。
涉及: crypto util + 账号体系依赖: V5.4 密码哈希先行验收: 反编译/localStorage均无明文敏感数据
