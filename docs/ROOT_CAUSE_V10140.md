# V10.14.0 根因分析报告 (ROOT_CAUSE_V10140)

> 版本: 10.14.0 (versionCode=101400) · 分析日期: 2026-09-04
> 范围: v10.13.0..v10.14.0 全部未发布变更(9提交) + 发版流水线阻断问题
> 方法: 现象→证据链→根因→验证,每条根因均有可复现证据与对应回归测试

---

## 0. 管理摘要

本次发版合并 4 类独立根因的修复:**3 个运行时核心问题**(组员秘钥丢失/镜像同步漏判/组员误配置污染)与 **1 个 CI 基建阻断问题**(映射表校验崩溃导致 main 与发版分支双线 CI 连续失败)。前三者由功能迭代引入,后者由数据同步工具重写 `vehicles_data.js` 声明格式引发——属于典型的"工具链演进未同步消费方"的基建回归。

---

## 1. 根因一: 组员端飞书秘钥永久丢失(清缓存后必须找管理员抄配置)

### 1.1 现象
组员点"清除缓存"或系统回收 WebView 内存后,`getFeishuCfg().appSecret` 变为空,同步链路永久失效,只能人工抄写配置恢复。

### 1.2 证据链
1. `hooks/before_build/01_inject_secrets.js` 在构建期把秘钥注入 `demo.html` 头部 `window.__BUILD_SECRETS__`
2. 旧版 `getFeishuCfg()` 读取后**立即 `delete window.__BUILD_SECRETS__`**(V10.12 的"用完即焚"防内存 dump 设计)
3. HTML 头部 `<script>` **只执行一次**——delete 后不会再有第二次注入
4. `localStorage.getItem('feishu_config')` 在清缓存场景下同样为空
5. → 两级存储同时失效,秘钥无第三处备份

### 1.3 根因
"用完即焚"的安全设计与"秘钥需要跨清缓存存活"的业务需求冲突,旧版没有为秘钥提供独立于 `window`/`localStorage` 的第三存储层。

### 1.4 修复与验证
脚本作用域私有闭包 `_INJECTED_SECRETS_CACHE`(首次读取浅克隆,delete window 引用不影响闭包)。回归测试 Z1/Z6/Z7(49 断言专项内):清 `localStorage` 后连续 4 次调用 `appSecret` 全等稳定;`window` 不暴露闭包变量。

## 2. 根因二: 镜像同步漏判(删除传播存在 3 类真机盲区)

### 2.1 现象
V10.11.0 已实现镜像同步,但特定时序下组长删除的车型仍不同步到组员端。

### 2.2 证据链(3 类盲区)
| # | 场景 | 旧版判定 | 结果 |
|---|---|---|---|
| ① | 同秒操作: 组长 14:00:03 上传(含删除),组员 14:00:03 已拉取过一次 | `cloudTs(3) > lastSyncTs(3)` = false | 删除永远不传播 |
| ② | 时钟回拨: 组长设备 NTP 校时跳回 5 秒后上传 | `cloudTs < lastSyncTs` = false | 全部修改漏同步 |
| ③ | 新装组员: 初始化 `lastSyncTs=Date.now()` | 云端历史时间戳恒小于 now | 首次同步不触发 |

### 2.3 根因
V10.11.0 的镜像触发条件**单一依赖时间戳比较**(`cloudTs > lastSyncTs`),而时间戳在真机环境(无 NTP 保证/秒级精度/本地时钟漂移)不是可靠的变化信号。

### 2.4 修复与验证
双通道 OR 决策: `needMirror = (cloudTs > lastSyncTs) || !sameIds`,其中 `sameIds` 为云端与本地车辆 ID 全集比较(差集即增删信号)。保留"云端=0台且本地>0台"熔断防误清空。回归测试 Z5 六子场景 + V1011 镜像 6 用例全绿。

---

## 3. 根因三: 组员端脏配置污染(历史垃圾值遮蔽注入秘钥)

### 3.1 现象
部分组员(尤其 V5.x→V10.x 跨版本升级)同步失败,排查发现生效配置是历史调试期写入的占位值。

### 3.2 证据链
1. 历史版本/调试路径曾把空串、占位符写入 `localStorage.feishu_config`
2. 旧版 `pick()` 逻辑"非空即取"(`saved.appSecret=' '` 也生效)
3. 优先级 `localStorage > injected` → 脏值**遮蔽**注入的正确秘钥
4. 组员端 UI 未做角色区分,输入框可编辑,组员"乱填试试"进一步写入新脏值

### 3.3 根因
配置读取缺少**角色信任模型**——组员端本不应有任何手动配置入口,但旧版把组长专属的配置页平铺给所有角色,且读取侧无条件信任 localStorage。

### 3.4 修复与验证
三层防御: ①`loadFeishuConfig` 三色横幅+成员态输入框 readonly/保存按钮隐藏; ②`saveFeishuConfig` 成员态直接 return(防 F12 绕过); ③`pick()` 成员态只信任 `_writer:'admin'` 标记的写入。回归测试 Z2/Z3/Z4/Z8/Z9/Z10。

## 4. 根因四: CI「映射表一致性校验」崩溃(发版流水线阻断)★本次发版新增

### 4.1 现象
main 分支 CI(2026-09-01 起)与发版分支 CI(2026-09-04 两次)连续失败,失败步骤固定为「映射表一致性校验(与vehicles_data.js无漂移)」,阻断一切合入与发布。

### 4.2 证据链
1. CI 日志(GitHub Actions run 33868717902 / 33489403006):
   ```
   Error: vehicles_data.js 中未找到 "const VEHICLES=" 声明
       at loadVehicles (scripts/gen_media_mapping.js:30:23)
   ```
2. commit 862fe97 用 `sync_feishu_local.js` 从飞书云端拉取重写了 `vehicles_data.js`,声明从 `const VEHICLES=[` 变为 `window.VEHICLES = [`(该工具写回时固定保持新格式,见 `sync_feishu_local.js:296`)
3. `gen_media_mapping.js:29` 的 `loadVehicles()` **单点硬编码** `src.indexOf('const VEHICLES=')` → 找不到声明直接抛错
4. 本地复现: `node scripts/gen_media_mapping.js --check` 以同样堆栈崩溃

### 4.3 根因
数据文件的生产者(`sync_feishu_local.js`)与消费者(`gen_media_mapping.js`)之间**无声明格式契约**。生产者升级了输出格式,消费者的解析是脆弱的单点字符串匹配,没有兼容层,也没有任何测试覆盖该解析路径。

### 4.4 修复与验证
`loadVehicles()` 改为正则双格式兼容: `/(?:const\s+VEHICLES\s*=|window\.VEHICLES\s*=)/`,历史/新格式均可解析。验证: 重新生成映射表(73 条记录与源数据一致)后 `--check` 退出码 0;映射记录本身无漂移(仅时间戳更新),证明此前 CI 失败纯属解析崩溃而非数据不一致。

### 4.5 防再发(Defense-in-depth)
- 正则同时覆盖两种格式,`sync_feishu_local.js` 后续写回新格式不再破坏校验
- 报错信息列出两种可接受声明,便于未来排查
- 本次发版后 CI 恢复绿色即是最直接的回归验证(见 TEST_REPORT §3)

## 6. 结论

四个根因分属三层: **业务层**(一/二/三,用户体验受损但可人工绕过)与**基建层**(四,自动化流水线完全阻断)。本次发版将四者一并闭环,并附带把 V10.12/V10.13 的发布文档补齐成套——避免"修复在代码里、知识在聊天记录里"的组织的熵增。
