## 二、问题清单（按严重度分级）

### 🔴 严重（P0：必须修复 / 立即优化）

#### P0-1 单文件单体 6,577 行 JS，维护成本指数级上升
- **现象**：241 个函数 + 11 个屏幕渲染 + 导出/同步/登录/审批 全部耦合在一个 `<script>` 块
- **影响**：
  - 认知负荷：新人通读一遍 ≥ 1 天，改一处需通盘回归
  - 合并冲突：多人协作时 100% 冲突（都改 demo.html）
  - 调试难度：Chrome DevTools 单步调试 7388 行文件，断点定位慢
  - 性能：WebView 冷启动一次性解析 6577 行 JS，低端 Android 设备首屏迟滞
- **根因**：V5.3~V10.11 共 12 个版本均在 demo.html 上增量累加，从未拆分

#### P0-2 飞书上传逻辑双轨并行（feishu-api.js ↔ demo.html），功能漂移风险
- **现象**：同一能力（分片上传/upload_all）两套实现：
  - [feishu-api.js:203-283](file:///e:/车辆断电指导应用开发/taicanggang-poweroff-guide/feishu-api.js#L203-L283)：`driveUploadFile` + `driveUploadFileMultipart`（~76 行）
  - [demo.html:1142-1369](file:///e:/车辆断电指导应用开发/taicanggang-poweroff-guide/demo.html#L1142-L1369)：`httpUploadFile` + `httpUploadFileMultipart` + `_uploadPartOnce`（~189 行）
- **差异点**（已证实）：
  | 维度 | feishu-api.js | demo.html |
  |------|---------------|-----------|
  | HTTP 栈 | `fetch` 原生 | Cordova `sendRequest` 优先 + fetch 降级 |
  | QPS 门控 | ❌ 未实现 | ✅ `_feishuQpsGate()` 220ms 串行 |
  | 事务过期重试 | ❌ 无 | ✅ 1061021 → 二次 prepare |
  | 失败降级 | `1061043` 升级分片 | `1061043` + Cordova 路径双保险 |
- **风险**：V10.10.0 大文件修复的 **QPS 门控/事务过期重试** 未同步到 `feishu-api.js`；如果未来代码切回 FeishuAPI 路线 → **大视频同步静默失败**

#### P0-3 机密硬编码（客户端可逆）
- **位置**：[demo.html:969-981](file:///e:/车辆断电指导应用开发/taicanggang-poweroff-guide/demo.html#L969-L981)
  ```js
  const _FS_XOR_KEY='tcg2026';                    // XOR 密钥明文
  appId:'cli_aa0ce4fd91f85be8',                    // AppID 明文
  appSecret:_fsDec('0750525c...222550'),           // Hex 密文 + 同一文件内解密算法
  ```
- **可恢复性**：拿到 APK / 源码 → 复制 970-976 的 `_fsDec()` + 981 的密文 → 浏览器控制台一行还原 AppSecret
- **现实危害**：飞书开放平台 AppSecret 泄露 = 可读取/删除「APP数据备份」目录所有文件、以应用身份发消息、创建审批实例
- **已防风险**：脚本侧 `scripts/*.py` 全部走环境变量（✅ 合格）；`feishu-api.js` 仅占位（✅ 合格）

#### P0-4 最大嵌套 8 层（L3639），认知过载 + 潜在 bug 温床
- **位置**：导出链路深层嵌套（推测 `generateDocxOOXML` / PDF 流程附近）
- **影响**：
  - McCabe 圈复杂度 ≥ 2⁸ = 256 条独立路径，人工覆盖 ≈ 0
  - 任意一层条件判断遗漏边界 → 数据丢失 / 导出静默失败
  - 单元测试无法独立覆盖分支

### 🟠 中等（P1：版本迭代中安排优化）

#### P1-1 innerHTML 27 处与 XSS 面

#### P1-2 全局状态无约束（VEHICLES / USERS / currentUser / navHistory）

#### P1-3 package.json 测试命令已过期（只到 V105）
- **现状**：`npm run test:all` = v57_logic/runtime/cross + v103 + v104 + v105
- **缺失**：V106（导出修复）、V107（防抖/权限）、V108（FormData 修复）、V109（视频分离/UI）、V1010（大文件分片）、V1011（镜像同步）

#### P1-4 函数体积超标（Top20 平均 79 行）
- Top 巨型函数清单：
  1. `pullPendingFromFeishu` 165 行（L4420）— 审批拉取 + 状态机 + 存储 = **4 个职责混合**

- **对比**：业界单函数建议 ≤ 40 行（单屏可见）

### 🟡 轻微（P2：有空就优化）

#### P2-1 内联 CSS 210 行 与 Tailwind 混用
- 现象：`.phone-frame`/`.screen`/`.scroll-y` 等自定义类与 Tailwind 共存，部分样式重复（如 `overflow`、`z-index`）
- 影响：改一处需两头核对

#### P2-2 117 个内联 `onclick` 无统一事件委托
- 性能：移动端 DOM 节点 × 117 事件监听 = 内存占用
- 可维护性：改 UI 时需同步改字符串，IDE 无法跳转引用

#### P2-3 Cordova 插件能力硬编码检测（`window.plugins`/`cordova.file`）
- 现象：14 处 `if (typeof cordova !== 'undefined') { ... } else { ... }`
- 建议：抽 `NativeBridge` 适配层，一处判断，全局使用

## 三、方案 A：渐进式重构（温和派 · 与业务迭代并行）

### 核心理念
> **不破不立，先拆后合**。每步改动独立可回归、可回滚；每个版本只做 1~2 项；不打断 V10.12 / V10.13 业务迭代节奏。

### 阶段划分（预计 3 个版本，共 4~6 周）

#### ✅ Phase A1：V10.12 — 去双轨 & 安全加固（风险最低、收益最高）
**目标**：消灭 P0-2 + P0-3 + P1-3

1. **飞书上传单向收敛**（消除 ~100 行重复）
   - 以 [demo.html:1142-1369](file:///e:/车辆断电指导应用开发/taicanggang-poweroff-guide/demo.html#L1142-L1369) 的「有 QPS 门控 + 事务过期重试 + Cordova 双栈」实现为真源
   - 反向移植到 `FeishuAPI`：
     - `driveUploadFile` 增加 1061043 自动升级分片（已有）
     - `driveUploadFileMultipart` 增加 `_feishuQpsGate` 串行门控 + `1061021` session 循环
     - 新增 `driveUploadFileSmart` 对应 `httpUploadFile` 的智能路由（≤16MB 直传/超标分片/超限自动升级）
   - demo.html 内部保留函数名（避免改 117 处 onclick），但函数体改为：
     ```js
     async function httpUploadFile(params) { return FeishuAPI.httpUploadFile(params); }
     async function httpUploadFileMultipart(params) { return FeishuAPI.httpUploadFileMultipart(params); }
     ```
   - **验证**：运行 V1010 分片 E2E 测试，`mock_feishu_server.js` 全量通过
   - **回滚成本**：= 0（函数签名不变，内部委托改为直接实现即可）

2. **测试命令补齐**（P1-3，1 小时）
   ```json

   "test:v106": "node tests/test_v106_fixes.js",
   "test:v107": "node tests/test_v107_fixes.js",

   ```
   - 同步更新 `.github/workflows/ci.yml` 的 test 步骤
   - **收益**：CI 自动覆盖 V53~V1011 全 15 个测试文件

3. **AppSecret 构建时注入**（P0-3 半量缓解，2 小时）
   - 不修改 Cordova 构建流程，最小改动：
     - 移除 [demo.html L969-981](file:///e:/车辆断电指导应用开发/taicanggang-poweroff-guide/demo.html#L969-L981) 的硬编码
     - 在 Cordova `before_build` hook 里从 `process.env.FEISHU_APP_SECRET` 读取 → 写入到 `window.__BUILD_SECRETS__`（放在临时 `<script>`，首屏执行完 `delete window.__BUILD_SECRETS__`）
   - **实际防护效果**：源码仓库无 Secret；拿到 APK 仍可反编译恢复（因为明文注入到 WebView JS），但**杜绝了「GitHub 泄露 → 自动爬虫抓 Secret」风险**（95% 的泄露场景）

#### ✅ Phase A2：V10.13 — 单文件拆分（P0-1，核心结构变更）
**目标**：demo.html 6577 行 JS → 拆为 7 个模块文件

拆分方案（按功能域，按屏幕×领域双维度）：

## 四、方案 B：架构升级（激进派 · 专门集中周期）

### 核心理念
> **推倒脚手架，重搭地基**。一次性引入现代工程化能力，彻底解决 P0/P1 全部问题。适合：项目空档期 2~3 周、可暂停业务迭代。

### 技术选型
| 维度 | 选型 | 理由 |
|------|------|------|
| 构建工具 | Vite 5 | 原生 ESM + 极速 HMR + 生产构建 Tree-shaking |
| 语言 | TypeScript 5 | 类型系统天然防 P1-2 状态越权、防拼错属性 |
| 框架 | React 19 + Vite | 声明式 UI 根除 innerHTML XSS（React 自动转义）；组件化替代 117 个 onclick |
| 状态管理 | Zustand 4 | 极简、无 Provider 嵌套、可追踪状态变更（根治 P1-2） |
| 路由 | TanStack Router | 强类型路由，navHistory 开箱即用（根治导航栈错乱） |
| 存储 | Dexie.js 4 | IndexedDB 强类型封装，替代 40 处 localStorage |
| 测试 | Vitest 2 + Testing Library | 覆盖率、并行执行、DOM 测试（补齐 CI 覆盖） |
| 静态检查 | ESLint 9 + Prettier | 一键 format / 捕获未转义 XSS / 捕获 eval |
| 安全 | 构建时 env + 代码混淆（Jscrambler，已有 workflow） | 根治 P0-3 客户端可逆 |

#### 🔷 Phase B2：领域层迁移（第 2 周）

2. **状态管理**（1.5 天）

   ```ts
     vehicles: [],
     add: (v) => set({ vehicles: [...get().vehicles, withId(v)] }),
     update: (id, patch) => set({ vehicles: get().vehicles.map(x => x.id===id ? {...x,...patch}: x) }),
     // ❌ 禁止直接改数组，所有变更走 action → 天然可追溯 + 可单测
   }));
   ```
3. **飞书 SDK 重构**（2 天）
   - 旧 `FeishuAPI`（IIFE）→ `FeishuService.ts`（类 + 单例 + 依赖注入 token 获取器）
   - 根治 P0-2：分片上传只有一份实现，单元测试覆盖 QPS 门控/事务过期

#### 🔷 Phase B3：UI 层迁移（第 3 周）
1. **11 个屏幕 × 组件化**（3 天）
   - Login/Register/Forgot → `pages/Auth/` 目录
   - VehiclesList/VehicleDetail/VehicleEdit → `pages/Vehicles/`
   - Data/Sync/My/Members/Password → `pages/Platform/`
   - 公共组件：`VehicleCard`、`BrandTabs`、`BottomNav`、`FAB`、`Toast`、`ConfirmModal`
   - **天然根治 XSS**：React JSX 自动转义 → 不用写 `esc()` → 27 处 innerHTML 风险归零
2. **导出模块迁移**（2 天）
   - `generateExcelSingle/Batch`、`generatePDFLegacy/Canvas`、`generateDocxOOXML`、`shareFile` → 纯函数放入 `services/exporters/`
   - 以 V10.11 导出文档作为黄金样例，写「字节级一致」回归测试

## 五、辩证对比：方案 A VS 方案 B

### 5.1 多维度量化对比

| **业务迭代中断** | ✅ **0 天**（每版本独立发） | ❌ 4 周无新功能上线 | **A 胜** |

### 5.2 辩证分析（正→反→合）

**正方（选 A）视角**：
> 项目是港口现场 App，核心诉求是**稳**。每版本都有现场真实反馈，任何一次架构级变更引发的回归都会直接影响作业效率。V10.8~V10.11 四次根因修复都证明：**增量修补 + 充分测试** 能在 0~1 天内根治问题。渐进式重构保持节奏不被打断，团队零学习成本即可持续交付。

**反方（选 B）视角**：
> 过去 V5.3→V10.11 共 12 个版本，每次都在 demo.html 上"打补丁"，**补丁套补丁** 导致 V10.8 才发现「删除同步从未实现（localIds 定义但没用到）」、V10.10 才发现「分片上传两套实现不一致」——这些都是**单文件无模块系统的结构性缺陷**，靠增量修补无法根治，只会继续冒出「没人敢改的大函数」。现在 V10.11 刚稳定，正是**窗口期**：如果等到 200+ 车型 / 30+ 组员的现场规模，再想换架构成本 ×3。

**合题（推荐路径）**：
> **A1 立即执行 + A2 紧随其后 + 评估是否需要 B 切换**。理由：
> 1. **A1（去双轨+测试补齐+Secret 注入）** 工作量 ≤ 3 天，0 风险，V10.12 就能带上。不做这步 = 继续承担 P0-2 大视频漏同步 + P0-3 Secret 泄露风险。
> 2. **A2（单文件拆 7 模块）** 是临界点：拆完后如果团队感到「已足够清晰，不会再踩结构性坑」，就**不必上 B**（省 4 周 + 学习成本）；如果拆完仍感混乱（全局函数 180+ 还是难定位），立即启动 B 方案，用拆文件的**领域边界**作为 React 组件拆分的**输入**——相当于 A2 做了 B 的需求分析前置。
