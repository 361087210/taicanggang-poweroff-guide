# V10.27.7 发版产物唯一性版

> 一句话：修掉飞书「发版产物」里同一个 APK/IPA 出现两份的问题 —— 既要它不再产生（并发串行化），
> 也要它自己能清掉（删全部同名 + 终验按唯一性判定）。

## 怎么发现的

发完 v10.27.6 去飞书核对交付，顺手看了下前几个版本目录：

| 目录 | 文件数 | 问题 |
|---|---|---|
| v10.27.6 | 4 | 正常 |
| v10.27.5 | 5 | `tcg_poweroff_v10.27.5_ios.ipa` **两份** |
| v10.27.4 | 4 | 正常 |
| v10.27.2 | 8 | **4 个产物全都一对二** |
| v10.27.1 | 5 | IPA 两份 |

三次出现、跨了好几个版本，说明不是偶发。

## 两个根因

**① 产生：并发覆盖上传。**
`Sync Release to Feishu` 同时挂在 Android 和 iOS 两条构建的 `workflow_run` 上。
两个构建耗时不同但可能非常接近 —— iOS 那条启动同步时，Android 那条还在上传，
两边都"先查同名 → 没有 → 上传"，各自插进一份。飞书允许同名文件共存，
所以没有任何一方报错。

**② 清不掉：聚合把副本吞成了 1 条。**
`list_children()` 返回的是 `{文件名: 文件对象}` —— 同名副本在这里被压成一条。
于是 `delete_if_exists()` 每次只删一条、再传一条，副本数恒定不减。
更糟的是终验只判断"名字能查到"，所以目录明明脏着，日志却一直是 `完成 ✔`。

## 改了什么

1. **串行化**（`.github/workflows/sync-release-feishu.yml`）：加
   `concurrency: {group: release-feishu-sync, cancel-in-progress: false}`。
   不取消进行中的任务 —— 取消可能停在半个文件上，让第二次在第一次结束后覆盖才安全。
2. **删全部同名**（`scripts/sync_release_to_feishu.py`）：新增 `list_children_all()`
   按名字分组保留全部项；`delete_if_exists()` 遍历删除并返回条数；多份时打印 `[清理]`。
3. **终验按唯一性**（单根 + 双根两处）：`在 且 只有一份` 才算通过；双根还额外扫全目录重名。
4. **存量清理**：手工清掉 v10.27.1 / v10.27.2 / v10.27.5 的多余副本，各恢复 4 件。

## 影响面

- 交付目录从此可核对："每个版本 4 件（apk / apk.sha256 / ipa / version.json），每件一份"
- 存量副本不需要单独跑迁移：该版本下次重跑同步时会自动清掉（本版之前的历史版本保持现状，
  已手工清理）
- 副作用：两个构建完成事件现在串行，第二次同步会等第一次结束（通常几十秒）
