## 一、问题现象

- 组长端新增车型后上传 → 组员端拉取可正常获取(正向合并已生效);
- 组长端**删除**车型后上传 → 组员端拉取后**已删车型仍然残留**,两端车型数量越差越大;
- 正确语义应为:同源同步,车型数量一致,数据同步增减。

## 二、根因分析

`doSyncDownload()`(demo.html 拉取同步入口)旧版合并逻辑是**单向并集合并(merge-only)**:

```
遍历云端 vehicles:
  本地已有同ID → 覆盖更新(updatedCount++)
  本地没有     → 追加(addedCount++)
【缺失】本地有而云端没有 → 应删除 → 旧版从未处理
```

关键证据:旧版第5515行 `const localIds=new Set(VEHICLES.map(v=>v.id))` 声明后**从未使用**——"删除同步"从设计上打算做但从未实现,历史遗留至今。上传侧无bug(`_syncUploadPipeline` 上传全量 `VEHICLES.map(...)`,组长删除后云端 `vehicleCount` 正确减少),问题仅在组员端拉取合并的反向差集缺失。

## 三、修复方案:镜像同步(云端为唯一真源)

### 1. 核心语义

拉取后本地与云端**完全对齐**——新增/更新/删除全量传播,组长组员车型数量严格一致。

### 2. 实现要点

| 机制 | 说明 |
|---|---|
| 正向差集 | 云端权威字段覆盖本地,`Object.assign({},local,sv)` 保留本地扩展字段,`pinyin` 重算 |
| 反向差集(核心) | 本地存在但云端已无的ID → 移除(删除传播) |
| 原地替换 | `VEHICLES.length=0` + `push`(const引用不可重赋),持久化/渲染闭包引用不失效 |
| 时间戳门控 | 仅 `cloudTs > lastSyncTs`(云端确有更新)时执行镜像——云端无变化时不误删组员本地导入的备份数据(V10.9.1 兜底通道兼容) |
| 防误清空 | 云端0条车但本地有数据 → 判定异常,拒绝镜像并红色日志告警(正常组长库至少含内置车型,不可能为空) |
| 三计数提示 | 完成通知显示「新增N条 更新N条 删除N条」,删改明细一目了然 |

### 3. 语义边界说明

- 组员端为只读角色(`canEdit()` 限制),本地不应有私有车型;组员唯一本地写入路径是"导入备份"(V10.9.1),该数据在云端有更新时会被镜像对齐覆盖——这是"同源同步"语义的预期行为,导入备份定位为离线应急通道而非长期数据源;
- 组长端自身拉取走同一管线:用自己的云端数据替换本地,幂等无害。

## 七、升级指引

1. 组长端与组员端均需升级至 V10.11.0(APK: `version.json` downloadUrl 或 GitHub Release v10.11.0);
2. 升级后组员端首次"拉取同步"即完成镜像对齐,历史残留的已删车型一次性清除;
3. 后续组长端每次增删改上传后,组员端拉取即同步增减,两端数量保持一致;
4. 组员端导入备份为离线应急通道:云端无更新时本地数据保留;云端一旦有更新,拉取后将按镜像语义与云端对齐。
